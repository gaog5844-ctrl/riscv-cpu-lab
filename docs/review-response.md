## 两条不能照做的建议

### JALR 不应因审查误判而改变异常归属

规范要求先计算 rs1 与立即数之和并清 bit 0，未对齐异常归属于跳转指令，而不是目标取指。规范没有规定必须在哪个流水级判断。此核心在 EX 才获得前递后的实际操作数，在这里判断与现有数据通路一致。

原例子 `rs1=0x80000001, imm=0` 的目标是 `0x80000000`。新用例对目标低位 2 和 3 分别检查：tval 为清 bit 0 后的地址，链接寄存器不写回，取指请求没有到达未对齐目标。已有 bit 0 清零测试仍保留，交替间接调用也使用置 bit 0 的函数地址。

来源：[RISC-V RV32I 2.1，Base Instruction Formats 与 Unconditional Jumps](https://docs.riscv.org/reference/isa/v20260120/unpriv/rv32.html)。

### FENCE 排序不等于原子回滚

标准 FENCE 约束访问顺序，不要求把八笔独立写入变成一个可回滚事务。本工程的全脏行写回是额外实现选择。写回错误前完成的字保持新值，未完成的字保持旧值，缓存保留完整脏行；当前 CPU 报告异常并停止执行，不是悄悄继续运行。

这不意味着支持完整错误恢复、掉电一致性或 DMA 一致性。需要这些能力时，应设计缓存之外的系统协议，不能只给 FSM 添加一个“回滚”状态就作保证。

来源：[RISC-V RV32I 2.1，Memory Ordering Instructions](https://docs.riscv.org/reference/isa/v20260120/unpriv/rv32.html)。

## 本次实际复现与修改

### 缓存配置加固

旧文档要求 enable 运行中不变，RTL 却直接读取实时引脚。新测试故意违反旧约定：写入脏行 0x12345678，再改变 enable，随后加载同地址。旧 RTL 返回 RAM 旧值 0xCAFE0000，测试失败。

现在 `rv32_dcache.enabled` 只在复位沿更新，该用例读取脏行中的 0x12345678；复位时禁用后再把引脚拉高也不分配缓存行。这是把已有配置约定落实为硬件行为，不声称实现了运行时缓存启停。

如果要保留 RAM 并切换模式，先成功 FENCE、停止新请求并排空在途事务，再复位配置。直接复位会丢弃缓存元数据，不能作为脏数据恢复手段。

证据：`tests/unit/tb_cache.sv`；本机 `build/review-cache-before.log` 与 `build/review-cache-after.log`。

### 提交比较器的真实漏检

外部报告泛泛讨论参考模型风险，没有指出以下具体问题。独立构造一条 store、一条 load、末尾 EBREAK 的合法提交轨迹，再只改一个字段。旧比较器会接受这五类损坏：

1. 正常提交带 trap 标志。
2. SW 写字节使能从 0xF 错为 0x1，但地址和数据不变。
3. 末尾异常带非零 rd。
4. 末尾异常带非零 data。
5. 末尾异常带非零存储字节使能。

`tests/spike_reference.py` 已显式拒绝上述情况；`tests/test_oracle.py` 保留 1 组合法轨迹和 15 种损坏轨迹。修复前出现 5 项负向测试失败，修复后全部通过。`tests/common.py` 同时检查 RAM dump 长度，避免短文件只产生不明确的比较异常。

这里证明的是比较器单独存在漏检，不是已发现 RTL 输出错误，也不是说原有整套验证必然放过这些情况。RTL 断言、退休数量和最终 RAM 检查是另外的防线。

## 审查报告中的其他事实错误

- 原综合报告是使用 4 个 DSP、器件可用 90 个，不是使用 0 个、可用 4 个。
- “35K”是器件型号系列标识，不能当作 35K LUT 容量；本次报告列出的 LUT 容量是 20,800。
- 原测试已有 CSR 与 FENCE.I 的非法指令检查、异常前正常提交比较、写回错误模块重试，以及 Python 生成的计算内核期望值。可以要求增强，不能写成完全不存在。
- 46 组测试并非所有缓存、预测、延迟、抖动选项的完整笛卡尔积；49 种正常指令类型也不等于全部微架构状态覆盖。
- 没有复现命令和新运行日志支撑的结论，不按“100% 确认”处理。分数不替代文件、代码路径和实验。
